# Environments and configuration

## Environments

Three, and only three. Adding a fourth has been proposed twice and refused twice,
on the grounds that every environment is a thing somebody has to keep working.

| Environment | Purpose | Data |
| --- | --- | --- |
| `dev` | Per-engineer, runs locally against Docker Compose | Seeded fixtures |
| `staging` | Pre-production, deploys on every merge to `main` | Anonymised snapshot, refreshed monthly |
| `prod` | Production | Real |

## Where configuration lives

Nothing is baked into the container image. Every environment-specific value is
read from the process environment at boot, and the values themselves come from
AWS SSM Parameter Store, injected by the ECS task definition. The rule is simple:
if a value differs between staging and prod, it is a parameter; if it does not, it
is a constant in the code.

## Parameter reference

This table says where each value comes from and how it is changed. It says
nothing about what the value *does* — for that, read the ADR that introduced it.
Several of these have burned somebody who assumed they knew what a variable meant
from its name alone.

| Variable | Secret? | Source | Changing it requires |
| --- | --- | --- | --- |
| `COGNITO_USER_POOL_ID` | No | `/wayfreight/{env}/cognito-pool-id` | A redeploy. Not a restart, not a config reload — the value is read once at boot |
| `WAYFREIGHT_SERVICE_JWT_SECRET` | Yes | Secrets Manager, rotated 90-daily | A redeploy of every service that holds it, in the same window |
| `TWILIO_VERIFY_SERVICE_SID` | No | `/wayfreight/{env}/twilio-verify-sid` | A redeploy |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | No | Task definition, points at the local collector sidecar | A task definition revision |
| `REDIS_URL` | Yes | Secrets Manager | A redeploy |
| `MAX_RETRY_BUDGET_MS` | No | `/wayfreight/{env}/max-retry-budget-ms` | A redeploy |
| `DATABASE_URL` | Yes | Secrets Manager | A redeploy |
| `OPENAI_API_KEY` | Yes | Secrets Manager, embedding worker only | A redeploy of the worker |

### On `MAX_RETRY_BUDGET_MS` specifically

It is a wall-clock ceiling, in milliseconds, on how long the ECS task will let a
single inbound request hold a worker before the platform gives up on it. Default
`30000` in every environment; we have never changed it. It is named unhelpfully
closely to a constant in the webhook delivery code that counts *attempts* rather
than milliseconds, and the two are entirely unrelated. At least two incidents have
started with somebody tuning one while thinking about the other, which is why the
error catalogue calls the pair out explicitly.

## Local development

`dev` reads a `.env` file that is git-ignored and generated by a script, so nobody
hand-maintains a list of eighteen variables and nobody commits a real
`COGNITO_USER_POOL_ID` by accident:

```bash
# scripts/pull-dev-env.sh
aws ssm get-parameters-by-path \
  --path /wayfreight/dev/ \
  --with-decryption \
  --query "Parameters[].{Name:Name,Value:Value}" \
  --output text | awk '{ n=$1; sub(".*/", "", n); print toupper(n) "=" $2 }' \
  > .env
```

## Database parameters are not application configuration

Worth stating plainly, because the two get conflated and the mistake is expensive.

Everything in the table above is *application* configuration: it is read by
core-api at boot, it lives in SSM or Secrets Manager, and changing it means a
redeploy. Postgres server parameters are a completely different animal. They live
in the RDS parameter group `wayfreight-pg15-params`, they are not in SSM, no
deploy touches them, and `shared_preload_libraries` in particular is not something
an application engineer changes as part of shipping a feature.

If you need a parameter-group change, that is a planned database change with its
own comms and its own window. The extensions note is the reference for what is in
`shared_preload_libraries` and why, and the maintenance runbook covers the rules
about touching the parameter group. Neither question has anything to do with this
document, and this document is not where the answer is.

## What is not configurable

Deliberately hard-coded, because making them configurable would mean staging and
prod could behave differently in ways nobody would notice until they did:

- The module boundary rules enforced at build time.
- The expand-contract migration sequence.
- Log level. `info` in every environment, `debug` nowhere, because a `debug` log
  level that can be flipped in production will eventually be flipped in
  production and left on.
