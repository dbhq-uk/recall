# Database migration policy

## Overview

Every schema change to `wayfreight-core-prod` goes through the same tool and the same review checklist, regardless of which module (`dispatch`, `tracking`, `billing`, `notifications`) it touches. This note exists because two separate production incidents in Wayfreight's first year - both self-inflicted, both avoidable - were caused by migrations that were correct in isolation but unsafe to run against a live, large table.

## Tooling

We use **dbmate** rather than an ORM-integrated migration tool, deliberately: migrations are plain `.sql` files, reviewable in a pull request without needing familiarity with any particular ORM's migration DSL, and runnable identically from a laptop, from CI, and from the deploy pipeline.

## Naming convention

Migration files are named `{timestamp}_{description}.sql`, for example `20250314091500_add_consignment_priority_flag.sql`, where the timestamp is generated by `dbmate new` at creation time. This guarantees a deterministic, chronological apply order across engineers working on separate branches without anyone having to hand-pick the next sequence number.

## Expand-contract for breaking changes

Any migration that would break a currently-deployed version of core-api - renaming a column, tightening a constraint, dropping a column that's still read - is forbidden from shipping in a single step. Instead we follow expand-contract across at least two deploys:

#### Expand

Add the new shape alongside the old one. A new `NOT NULL` column on a table over one million rows is never added as `ADD COLUMN x NOT NULL` directly, because that rewrites the entire table under an `ACCESS EXCLUSIVE` lock; instead we add it nullable with a default, backfill in batches, and only then add the constraint.

#### Migrate

Deploy application code that writes to both shapes and reads from the new one, and backfill existing rows in bounded batches so a single transaction never locks more than a few thousand rows at a time.

#### Contract

Once the previous application version is no longer running anywhere (confirmed via the deploy history, not assumed), drop the old shape in a follow-up migration.

```sql
-- step 1 (expand): safe on a large table, no full rewrite
ALTER TABLE consignments ADD COLUMN priority_flag boolean DEFAULT false;

-- step 2 (migrate): backfill in batches of 5000, run outside a single transaction
-- so a long backfill never holds one lock for its entire duration
UPDATE consignments SET priority_flag = false
WHERE id IN (
  SELECT id FROM consignments WHERE priority_flag IS NULL LIMIT 5000
);

-- once every row is backfilled, validate the constraint without a full table lock
ALTER TABLE consignments ALTER COLUMN priority_flag SET NOT NULL;
```

The 1,000,000-row threshold isn't arbitrary - it's roughly where, in our testing against a production-sized `tracking_events` clone, a single-statement rewrite started taking long enough to risk tripping our statement timeout and blocking foreground writes for other requests.

## Rollback requirement

Every migration file must have a corresponding down migration, and CI enforces this by running `dbmate up`, then `dbmate down`, then `dbmate up` again against an ephemeral database for every pull request that touches `db/migrations/`. A migration missing a down file fails that CI step with `ERR_MIGRATION_NO_DOWN` rather than merging silently without one.

```bash
# what CI actually runs for migration-touching PRs
dbmate up
dbmate down
dbmate up
```

## Review checklist

Reviewers check three things on every migration PR: does it lock a table for longer than a few hundred milliseconds, does it have a tested down migration, and if it's a breaking change, is it actually step 1 of an expand-contract sequence rather than a single combined change.
